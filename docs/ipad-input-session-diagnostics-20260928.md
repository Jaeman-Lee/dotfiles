# iPad 한글 입력 및 Codex 세션 연결 진단

문서 원본은 이 파일이다. 지정 Obsidian Vault 연결은 미설정이다.
요구사항·진행 상태: [이슈 #20](https://github.com/Jaeman-Lee/dotfiles/issues/20).
최종 기록·입력 개선 검토: [draft PR #23](https://github.com/Jaeman-Lee/dotfiles/pull/23).
초기 진단 기록: [커밋 fb25194](https://github.com/Jaeman-Lee/dotfiles/commit/fb25194).
기존 입력 운영 절차는 [Ubuntu 웹 원격 화면](ubuntu-web-desktop.md#ipad)을 따른다.
실행 로그·대화 원문·세션 식별자·인증 정보는 기록하지 않는다.

## 이번 작업의 마감

2026-09-28 사용자 요청에 따라 이번 원격 테스트와 진단은 여기까지 진행하고 Git 기록을 남긴다.
운영 배포·서비스 재시작·PR 병합은 수행하지 않는다. 해결되지 않은 항목은 이슈에서 후속 보류로 유지한다.

- iPad의 기존 **글쓰기 → 전송** 경로에서 긴 한글 문장이 정상 수신되는 것을 사용자와 확인했다.
- 사용자는 글쓰기 클릭 후 간헐적으로 PC 터미널로 입력되는 현상도 보고했다.
  포커스 보호·접기 수정과 Ctrl+Enter 전송은 구현 및 검증을 마쳤지만 **운영에는 미적용**이다.
  구현·검증 원본은 [운영 문서의 변경 기록](ubuntu-web-desktop.md#글쓰기-포커스-보호와-ctrlenter--2026-09-28)을 따른다.
- 직접 입력의 편의성을 우선하고 글쓰기는 보조 수단으로 남기는 방향을 사용자가 선호했다.
  직접 입력 개선은 구현하지 않았다. 실제 브라우저와 외장/화면 키보드 구분도 확인이 남았다.
- 빨간 `Reconnecting…`에 대응하는 실제 모델 응답 연결 종료 및 재시도 기록을 확인했다.
  아래 두 건은 후속 작업 완료까지 확인했으나, 모든 세션의 안정성이나 반복 장애의 근본 원인이 해결된 것은 아니다.

## 초기 확인 결과

14:47–14:51 KST에 읽기 전용으로 확인했다. 해당 시점의 관측이며 간헐적인 장애를 배제하지 않는다.

- CPU 유휴 비율 약 90%, 가용 메모리 약 6.9 GiB였다. 지속적인 전체 자원 포화는 관찰되지 않았다.
- SSD swap 8 GiB 중 약 6.9 GiB가 사용 중이었지만 표본 구간 swap-in은 초당 약 12–36 KiB,
  swap-out은 0이었다. swap 사용량 자체를 현재 지연 원인으로 단정하지 않는다.
- 기본 게이트웨이 ICMP 5회는 손실 0%, 평균 약 0.22 ms였다. iPad에서 PC까지의 원격 구간 측정은 아니다.
- ChatGPT Codex 경로는 비인증 HEAD 요청에 405로 응답했다. 연결 도달만 확인하며 모델 응답 성공을 뜻하지 않는다.
- 기존 Codex 터미널 프로세스 세 개에서 `account/rateLimits/read timed out in TUI`가 반복됐다.
  로컬 제어 소켓의 handshake 미완료 및 연결 해제 로그도 있었다. 이 기록만으로 모델 요청 실패 원인을 확정할 수 없다.
- 현재 진단 세션은 모델 응답과 도구 실행이 가능했다. 기존 세 세션이 복구되었다는 증거는 아니다.
- `codex app-server daemon version`에서 CLI 0.157.0, 실행 중 daemon 0.158.0을 확인했다.
  버전 차이는 추가 확인 대상이며 호환성 문제가 원인이라고 단정하지 않는다.

## 한글 입력 안내

기존 운영 문서에는 Guacamole Text input 경로에서 한글 누락과 PC 입력기의 영문 재해석을
실제 호스트에서 재현한 기록이 있다. iPad 사용자는 하단 **글쓰기**의 흰 입력칸에서
문장을 완성하고 **전송 ↵**을 누르는 기존 기능을 우선 사용한다.
후속 확인에서 이 입력칸을 통한 한글 문장 전송은 성공했다. 간헐적인 포커스 문제는 별도로 보고되었다.

## 초기 진단의 검증 범위

`node --test remote-desktop/tests/mobile-input.test.cjs`: 기존 회귀 테스트 9개 통과.
이는 전송 순서·중복 방지·초안 보존 검증이며 iPad 실기기 한글 조합 성공을 증명하지 않는다.

초기 진단에서는 소스 코드, PC 입력기 설정, 원격 서비스와 Codex 실행 상태를 변경하지 않았다.
기존 세션이나 daemon을 재시작하지 않았다. 미전송 입력과 실행 중 작업을 보존했다.
후속 소스 수정과 17개 회귀 테스트 결과는 운영 문서에 기록했으며, 운영 서비스는 계속 유지했다.

## Codex 재접속 후속 확인

2026-09-28 22:12–22:17 KST에 보존된 로그와 작업 완료 이벤트를 읽기 전용으로 확인했다.
다음 시각은 모두 KST이며, 확인 가능한 사례만 기술한다.

| 시각 | 관측 | 확인 범위 |
| --- | --- | --- |
| 09-27 19:57:36, 20:58:13 | 응답 WebSocket의 60분 연결 제한에 도달했다는 오류 후 재시도 | 이 두 건의 재접속 사유가 오류에 명시되어 있다. |
| 09-28 18:30:18 | 응답 완료 전 `Connection closed normally`로 연결 종료, 재시도 1/5 | 같은 대화의 작업 완료 이벤트가 18:30:52에 기록되어 약 34초 뒤 완료를 확인했다. |
| 09-28 19:38:04 | 같은 연결 종료와 재시도 1/5 | 작업 완료 이벤트가 19:38:18에 기록되어 약 14초 뒤 완료를 확인했다. |
| 09-28 22:11:48, 22:11:57 | 로컬 제어 소켓의 WebSocket handshake 미완료 | 앞선 모델 서버 응답 연결 종료와 동일한 원인이라고 단정하지 않는다. |

`Connection closed normally`는 연결 종료 방식의 설명이며, 답변 생성이 성공적으로 끝났다는 의미가 아니다.
오늘 두 건에서 연결을 닫은 근본 원인이 서버인지 네트워크인지 로그만으로 확정할 수 없다.
별도로 여러 터미널에서 `account/rateLimits/read` 시간 초과가 반복되었다.
이는 조회 응답이 지연된 기록이며, 사용량 한도를 소진했다는 증거는 아니다.

원격 웹 컨테이너는 확인 당시 약 23시간 연속 실행 중이었고 OOM 종료 흔적은 없었다.
GNOME 원격 서비스도 유지되어 있었다. 이번 작업에서 원격 웹·Codex daemon을 재시작하거나
수정본을 운영에 적용한 사실은 없다. 이 관측만으로 과거의 모든 네트워크 끊김을 배제하지 않는다.
