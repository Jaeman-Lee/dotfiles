# SSD 개발 저장소 적용 기록

Vault 연결 미설정. 이 Git 문서가 기록 원본이며, 실제 작업 상태는 [이슈 #8](https://github.com/Jaeman-Lee/dotfiles/issues/8)에서 관리한다.

## 관측과 변경

- 사용자가 기존 SSD 데이터 불필요 및 초기화를 승인하고 준비 스크립트를 직접 실행했다.
- Samsung SSD 980 500GB의 단일 ext4 파티션이 `/mnt/dev-ssd`에 `rw,noatime`으로 마운트되어 있다.
- SSD에서 사용 가능한 공간은 약 453GiB다. Ubuntu의 `/`, `/boot`, `/boot/efi`는 기존 HDD에 있다.
- `/etc/fstab`의 SSD 항목은 마운트 UUID와 일치하며 한 번만 등록되어 있다. UUID를 `.storage-ready`와도 대조했다.
- worktrees, projects, builds, npm/pip/uv 캐시 디렉터리는 개발 사용자에게 쓰기 권한이 있다.
- `storage/use-ssd.sh`로 `~/.config/environment.d/60-dev-storage.conf`를 설치했다. 비밀정보는 포함하지 않는다.
- 사용자 systemd manager를 reload한 뒤 새 사용자 서비스에서 `npm config get cache`가 `/mnt/dev-ssd/cache/npm`을 반환했다.
- pip/uv의 캐시 경로도 설정했지만 두 도구의 설치·실제 캐시 동작은 이번에 검증하지 않았다.
- 기존 실행 중 서비스의 환경과 캐시는 강제로 재시작하거나 이동하지 않았다.

## 검증

| 검사 | 결과 |
|---|---|
| ext4 마운트·쓰기 옵션 | PASS |
| fstab UUID와 실제 마운트 UUID 일치 | PASS |
| 개발 디렉터리 사용자 쓰기 권한 | PASS |
| SSD에서 1MiB 쓰기·fsync·재읽기 SHA-256 비교 | PASS, 임시 검증 파일 정리 |
| SSD에 실제 Git 작업 브랜치/worktree 생성·status | PASS, `/mnt/dev-ssd/worktrees/dotfiles-ssd` |
| 새 사용자 서비스의 npm 캐시 경로 | PASS |
| 주기적 TRIM 타이머 | enabled / active |
| fstab 정적 검사 | parse error 0, error 0. 비관리자 실행에 따른 장치 접근 경고와 systemd reload 경고 있음 |
| 시스템 manager reload | NOT_DONE: 제공된 인증 파일을 통한 sudo 인증 실패 |
| 재부팅 후 자동 마운트 | NOT_TESTED: 이 작업에서 PC를 재부팅하지 않음 |

인증 파일 내용은 출력하거나 Git에 기록하지 않았다. 파일 권한은 소유자만 읽고 쓸 수 있도록 제한했다.
인증 실패 후 비밀번호 추측이나 반복 시도는 하지 않았다.

## 후속 실행과 배치

시스템 관리자 인증이 가능한 터미널에서 다음 명령으로 현재 systemd의 mount 설정을 새로 읽는다.

```sh
sudo systemctl daemon-reload
sudo findmnt --verify
```

초기화 스크립트는 다시 실행하지 않는다. 이후 실행을 위해 준비 스크립트에는 fstab 변경 뒤 systemd reload 단계를 추가했다.
재부팅 검증은 다음 정상 재부팅 시 마운트 UUID·권한·캐시 경로를 확인해 기록한다.

새 작업은 SSD worktree에서 진행한다. 기존 원본 저장소와 Git object DB는 HDD에 있으며 새 worktree와 object를 공유한다.
전체 저장소나 실행 중 서비스의 이동은 경로 의존성과 복구를 확인한 후 수행한다.
HDD는 기존 OS·원본 저장소·백업 및 보관 자료를 유지한다. 백업은 다른 물리 매체의 복사본과 복원 검증이 별도로 필요하다.
